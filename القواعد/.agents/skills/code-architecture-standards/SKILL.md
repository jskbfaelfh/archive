# Code Architecture & Engineering Standards

## 1. Mandatory First Line Header
Every single code file (`.ts`, `.tsx`, `.css`, `.dart`, etc.) must start with this exact line at line number 1:
```typescript
// يجب قراءة ملف قواعد كتابة الكود قبل كتابة أي سطر في الملف
/**
 * @file [Clear File Name]
 * @description [Precise architectural description of the file's role]
 * @created 2026-09-15
 * @modified 2026-09-15
 */
```
*(For pure CSS/SCSS files, use standard CSS comment syntax: `/* يجب قراءة ملف قواعد كتابة الكود قبل كتابة أي سطر في الملف */`)*

## 2. Strict Rules Matrix (Architecture & Core Logic)

### Rule 1: Strict 300 Lines Ceiling (Universal Multi-Language Hybrid Enforcement)
- Strictly prohibit exceeding 300 lines of code in any single file across ALL languages (`.ts`, `.tsx`, `.dart`, `.py`, `.php`, `.c`, `.cpp`, `.cs`, `.java`, `.go`, `.rs`, `.css`).
- Automatically validated via `npm run check:lines` (and enforced automatically during builds).
- **Workflow & Early Warning:** If any file approaches 220-250 lines (the script automatically flags warnings at 230 lines), immediately refactor it into smaller modular units, custom hooks, or services.
- The Agent must execute `npm run check:lines` whenever creating or heavily editing files across any supported language.

### Rule 2: Detailed Comments & Timestamps
- Write detailed comments explaining the logic and architectural intent for every function, state, or effect.
- Maintain creation and modification dates in file headers.

### Rule 3: High Quality, TypeScript Strict & Clean Architecture
- Enforce full TypeScript Strict Mode with zero usage of the `any` type.
- Enforce strict separation of concerns across directories:
  - Types: `types/`
  - Services & Data: `services/`
  - State Management: `context/` & `hooks/`
  - Common Components: `components/common/`
  - Layout Components: `components/layout/`
  - Screens & Pages: `pages/`

### Rule 4: Continuous Detailed Documentation
- Document every request and milestone thoroughly with timestamp in `DOCUMENTATION.md`. Never omit any requested or implemented feature.

### Rule 5: Explicit Naming Convention
- Name any file, component, interface, function, or variable explicitly and semantically in English. No ambiguous abbreviations.

### Rule 6: Don't Repeat Yourself (DRY)
- Never duplicate code, logic patterns, or queries. Consolidate shared elements into reusable components.

### Rule 8: Zero Errors & Warnings Policy
- Perform rigorous testing on every built piece. Verify successful bundle compilation with 0 Errors and 0 Warnings in console/build logs.

### Rule 9: Universal Fault Isolation & Graceful Error Recovery
- **Universal Crash Prevention:** Never allow an unhandled runtime error in a sub-widget, service, or individual API request to crash or white-screen the entire application.
- **Strict Blast-Radius Containment:**
  - In frontend frameworks (React, Flutter, Vue): Wrap distinct functional modules, widgets, and dynamic panels in dedicated Error Boundaries or localized error-catching wrappers.
  - In backend & services (Node, Python, PHP, Dart): Implement defensive service layers with safe fallbacks and structured error responses.
- **Graceful Fallbacks:** If a component or service fails, render a localized, non-blocking fallback card or retry prompt without disrupting surrounding layout or unrelated tabs/modules.

### Rule 10: Type Safety & Runtime Validation (Zod Schemas)
- Static types (`TypeScript interfaces/types`) provide compile-time safety, but external data must be validated at runtime.
- **Mandatory Runtime Validation:** All payloads entering the system (external APIs, SIS integrations, user inputs, LocalStorage states, URL queries) MUST be parsed and validated through runtime schema validators (e.g., **Zod** in TypeScript, **Pydantic** in Python, or equivalent model serializers).
- **Graceful Parsing:** Use `.safeParse()` instead of throwing unhandled exceptions. If external data structure changes or becomes corrupted, handle fallback defaults gracefully without cascading failures.

### Rule 11: Atomic Commits & Conventional Commits
- All Git commit messages generated by the Agent or developer must strictly adhere to the **Conventional Commits** specification:
  - Format: `<type>(<scope>): <clear descriptive imperative summary>`
  - Allowed types:
    - `feat:` A new user-facing feature or enhancement.
    - `fix:` A bug fix or correction.
    - `refactor:` Code restructuring without changing behavior or adding features.
    - `style:` Formatting, UI polish, CSS adjustments with zero logic change.
    - `docs:` Documentation changes only.
    - `chore:` Maintenance, build configs, dependencies, or script updates.
  - Example: `feat(timetables): add real-time hall conflict detector`
  - Commits must be **Atomic**: small, cohesive, focused on a single logical change, and never combine unrelated refactoring with feature additions.

### Rule 13: Academic Domain Logic Integrity
- Maintain full institutional workflow logic:
  - 5-stage academic timetable approval lifecycle.
  - Real-time conflict detector for halls and faculty across all university colleges.
  - Strict hierarchical permissions (University Presidency, College Deanery, Department Council).

### Rule 14: Safe Migration & Preservation
- When migrating code to React + TypeScript, never delete original legacy files. Archive them inside `_legacy_vanilla_mvp/`. Do not delete old files until the new version is fully verified and explicit user permission is granted.

### Rule 16: API Integration & Security Isolation
- **Dedicated Endpoint per Database Function/Operation:** Create dedicated API endpoints for external integrations (SIS, HR, LMS like Moodle).
- **Independent Integration File:** Maintain all integration links in code (`src/constants/apiEndpoints.ts`) and documentation (`docs/روابط_التكامل_الخارجي_API.md`), updated automatically.
- **Complete Internal Security Isolation:**
  - Internal APIs (`/api/v1/internal/...`): Secured via encrypted user sessions and secure cookies, restricted internally.
  - External APIs (`/api/v1/external/...`): Isolated in separate routes, protected by API Keys/Bearer Tokens, granular scopes, and Rate Limiting.

### Rule 20: Complete Feature & Functional Parity
- Retain all operational features without exception (e.g., collapsible desktop sidebar, advanced filtering, hierarchical lock indicators, printing mechanisms, localStorage state saving).

### Rule 37: Dual-Layer Frontend & Backend Mandatory Validation
- Implement strict validation on both Frontend (UI guidance, reactive borders, blocking empty submissions) and Backend/Services (service-level and database rules to prevent invalid payloads). Never allow invalid states like empty timetables to be escalated.

### Rule 43: Strict Zero Unauthorized Deletions & Feature Preservation
- Strictly prohibit deleting, removing, disabling, or stripping any existing functional feature, UI component, input, or option built previously unless explicitly requested in writing. All improvements must be built on top of existing features.

### Rule 44: Phone Input Strict Digits-Only, Fixed Iraq Prefix (+964) & 11/10 Digits Monitoring
- **Digits-Only Restriction:** All phone number inputs system-wide must exclusively accept numerical digits (`0-9`). Any letters, symbols, punctuation, or spaces must be actively rejected on keystroke (`onKeyDown`), change sanitization (`value.replace(/\D/g, '')`), and clipboard paste (`onPaste`).
- **Leading Zero Monitoring (11 Digits with 0, 10 Digits without 0):** Actively monitor the leading digit: if the phone number begins with `0`, the allowed length is strictly 11 digits. If it starts with any other digit (non-zero), the length is strictly 10 digits. Input past this dynamic threshold is actively prevented.
- **Fixed Iraq Prefix (+964) on Far Left:** The Iraq country code `+964` must be permanently locked on the far left of the field with the plus sign at the very left edge, remaining strictly fixed in position regardless of RTL or LTR document direction.
- **Centralized Architecture:** Enforced via `src/components/common/PhoneInput.tsx` and centralized validation utilities `src/utils/phoneValidation.ts` (`getPhoneMaxDigits`, `sanitizePhoneNumber`, `isPhoneNumberComplete`).
